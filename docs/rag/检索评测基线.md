# 代码 RAG 检索评测基线

## 评测目标

当前评测用于防止索引、Tokenization、BM25、向量排序或融合逻辑在重构后退化。它不是公开 Benchmark，也不能证明系统已经具备生产级代码语义检索能力。评测入口为：

```text
python scripts/run_retrieval_evaluation.py . --k 5
```

## 指标

- `Recall@K`：前 K 个结果中是否至少存在一个相关文件和符号。
- `MRR`：第一个相关结果排名的倒数均值。
- `Precision@K`：返回结果中相关结果的比例。

## 当前确定性用例

单元测试使用认证和计费两个极小模块做确定性门禁；独立 CLI 使用 `retrieval_eval_cases.json` 中三条人工核验的当前仓库用例，分别定位 Workflow 恢复、Context Token Budget 和 Tool 权限。

| Query | 相关文件 | 相关符号 |
|---|---|---|
| authentication token validation | `auth.py` | `validate_token` |
| calculate invoice total | `billing.py` | `calculate_invoice` |

当前自动化门禁要求：

- `Recall@3 = 1.0`
- `MRR = 1.0`

## 当前仓库实测基线

2026-09-15 在当前仓库、默认 `HashEmbeddingProvider`、`K=5` 下运行：

| Mode | Recall@5 | MRR | Precision@5 |
|---|---:|---:|---:|
| BM25 | 0.667 | 0.233 | 0.200 |
| Vector | 0.333 | 0.083 | 0.067 |
| Hybrid | 0.333 | 0.167 | 0.200 |

该结果明确说明默认哈希向量没有带来语义检索优势，且当前三条样本不足以调参或得出统计结论。它不能被写成“Hybrid 提升了 XX%”。配置真实语义 Embedding 后，应在同一人工标注集合上重新运行并扩充样本，再决定默认参数。

## 局限

当前数据集规模很小，部分查询与源码存在词法重叠。接入真实 Embedding 后，需要增加同义表达、跨文件调用、配置定位、错误日志定位和多语言项目用例。当前 JSON 已与实现代码分离，并通过 `verification` 标记人工核验来源；后续自动生成用例必须使用不同标记，不能混入正式结论。
